Medusa

An experiment in distributed NUMA on Linux

x86-64 Linux · C++20 · GPL-2.0-only

Abstract

Medusa studies two ways to use a remote CPU. An ordinary single-threaded program can move to another host and keep its PID and open files. A program built with libdnuma can run threads on both hosts at once and share a region of memory. In both cases the master coordinates the work, and each remote host runs an agent on stock Linux.

Design

Process export

An agent runs the user-mode instructions of an eligible single-threaded process and fetches its pages on demand. The PID, file descriptors, and terminal remain on the master, where the original process executes forwarded system calls. Recall returns the modified pages and resumes the process on the master. With --auto-export, the master looks for eligible CPU-bound processes when local CPUs are oversubscribed and an agent has spare capacity. An operator can also select one of the agent’s CPUs with dnumactl export PID --cpu ID. Process export notes

Shared pages and thread placement

A thread that reads a distributed page for the first time can fault it in over RDMA. Several hosts can keep read-only copies of the same 4 KiB page, even when the program has permission to write it. On the first write, the master waits for the other hosts to discard their copies before granting the writer exclusive access. Page ownership protocol

When a writable page repeatedly changes hands between two runtime-managed threads, the master can ask one to move closer to the other. This applies to threads created with automatic placement. The thread moves at its next call to dnuma_migration_point(). Thread migration

Native threads and Go

An experimental master-kernel patch lets an external pager revoke a private heap page while the application’s other threads keep running. The remaining step for a stock Go program is to give its Linux threads one coherent address space across hosts and preserve their affinity, futex waits, and signals as they move. Today those threads run together on one host. Native thread support

Validation and limitations

The two-host export suite checked an exact remote CPU pin, a checksum of a file held only on the master, and memory contents after recall. In a separate libdnuma test, readers on both hosts observed 3,000 writes with no stale reads detected. The locality policy also moved a managed thread.

In a Linux 7.3.5 VM, a Go process completed 128 heap-page eviction cycles while garbage collection ran. A separate test in the same VM alternated ownership of a page 256 times between a pthread process and a Go process. Both readers saw the preceding writer’s value. Reproduce the native pager tests

Hardware tests used one physical agent at a time. Multi-agent tests used simulation or a second agent on the master. Ordinary Linux sched_setaffinity() accepts local placement. Setting a remote-only mask from an application remains open.

Build and reproduce

The build requires x86-64 Linux, g++ 11 or later, CMake 3.20 or later, Ninja, and the libibverbs and librdmacm development files. The unit tests run without RDMA hardware.

git clone https://github.com/adamdeprince/medusa.git
cd medusa
scripts/kernel-headers.sh
cmake -S . -B build -G Ninja \
  -DDNUMA_KERNEL_HEADERS="$PWD/.deps/linux-7.3.5-headers/include"
cmake --build build
ctest --test-dir build

To try process export, follow the cluster setup instructions to attach an agent over InfiniBand. On the master, start a checksum on a file large enough to keep the job running during export.

sha256sum large-file.iso &
pid=$!
dnumactl export "$pid"
dnumactl process list
dnumactl recall "$pid"
